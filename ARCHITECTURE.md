# disco-graph V3 Architecture

## Goal

Given a Git repository, branch and coding task, disco-graph should gather the smallest useful amount of repository context, modify code safely in an isolated worktree when requested, execute relevant validation, and stop with a clear diff. V3 combines Graphify's AST-derived knowledge graph with compiler-aware symbol resolution, role-specific agent execution, and benchmark measurements.

## Components

### FastAPI API

Entry point for cloning, indexing, manual graph experiments, autonomous agent runs and strategy benchmarks.

### Repository Manager

Clones an HTTPS branch into `/workspace/<uuid>`, where the UUID v4 `repo_id` is generated by the service for every clone request. Optional PAT credentials are passed via `GIT_ASKPASS` and are not persisted in the remote URL. The generated ID is returned to the caller for subsequent API requests.

### Graphify Service

Runs `graphify extract . --code-only`, loads `graphify-out/graph.json`, generates a Sigma.js/Graphology `graphify-out/graph.html` viewer, uploads both artifacts to MinIO under `disco-graph/<repo-id>/graphify-out/`, and exposes graph state. The local files remain a working cache; if they are missing, the service restores them from MinIO before graph retrieval. The index is marked stale when source files are newer than the graph.

### Graph Artifact Storage

MinIO is configured as an optional S3-compatible artifact store. The Docker Compose profile enables it with bucket `disco-graph-artifacts` and object prefix `disco-graph`. `MINIO_REQUIRED=true` makes indexing fail when upload cannot complete; the default `false` keeps local graph operation available during a MinIO outage. `MINIO_PUBLIC_ENDPOINT` controls the host used in temporary browser URLs, which is separate from the endpoint the API container uses to reach MinIO. `MINIO_REGION` is set explicitly so presigned URL generation does not require a network lookup through the public endpoint.

### CodeGraph

A dependency-free graph reader with:

- support for `nodes` plus either `links` or `edges`,
- lexical seed ranking,
- bounded context BFS,
- relation/confidence filters,
- neighbor expansion,
- shortest paths,
- retrieval diagnostics.

Traversal is context-bidirectional while every returned edge preserves its original source/target direction. This is deliberate: when understanding unfamiliar code, incoming callers/importers can be as important as outgoing dependencies.

### Symbol Resolver

`resolve_symbol` gives the agent a definition-first path before broad scanning. It combines:

- Graphify symbol metadata when a graph exists,
- Python `ast` parsing for class/function definitions,
- static TS/JS/Java-style definition patterns,
- cheap compiler/project probes such as `go list` and `tsc --noEmit` when available.

The resolver reports candidates with path, line, source and confidence so benchmark traces can distinguish graph, static and compiler evidence.

### Adaptive Retrieval Contract

`graph_query` accepts an explicit BFS `depth`. It returns evidence plus diagnostics:

- `sufficiency_score`
- `query_token_coverage`
- `source_file_count`
- `node_count`
- `edge_count`
- `sufficient`
- `recommended_next_depth`

The score is deliberately heuristic. It estimates whether the retrieved graph slice is broad enough to continue investigation; it does not judge whether the code answer is correct.

The LLM decides among four reactions to weak evidence:

1. expand by one BFS hop,
2. reformulate the graph seed query,
3. switch to lexical search for exact text/configuration,
4. rebuild a missing/stale graph.

### Role Agents

The runtime wraps one model decision interface with separate Planner, Coder and Reviewer role agents:

- Planner gathers the smallest useful evidence trail.
- Coder makes focused source edits.
- Reviewer validates the diff through targeted commands or inspection.

Each model call still chooses exactly one next action. Tool events are tagged with the responsible role, and the model receives only user-safe action summaries and tool observations, not hidden reasoning. The loop ends when the model emits `finish` or the step limit is reached.

### Worktree Isolation

When `isolated_worktree` is enabled, disco-graph creates a detached Git worktree under `.disco-graph-worktrees` next to the cloned repository. The original checkout remains unchanged; responses include the active worktree path and the diff from that worktree. Benchmark runs always use isolated worktrees.

### Measurements

Agent responses include elapsed time, tool calls, tool-output characters, LLM token usage, reasoning/cached-token details when the provider returns them, and configurable cost estimates. Cost settings are explicit environment values because model pricing changes.

### Repository Tools

Direct source operations remain available because graph retrieval is not authoritative:

- repo map
- compiler/static symbol resolution
- ripgrep
- file reads
- unified-diff patching
- allow-listed build/test commands
- git diff

## Trust model

Graph edges are useful evidence, not executable instructions. `EXTRACTED` edges indicate explicit structural relationships; `INFERRED` edges are leads that should be verified in source when correctness matters.

Source code and test/build outcomes are authoritative after edits. Because graph data can become stale following a patch, the agent is instructed not to rely on the old graph for post-edit structural claims without rebuilding.

## Why disco-graph owns BFS depth

Graphify provides a strong AST graph and its CLI can query that graph, but disco-graph needs a visible, controllable retrieval policy for agent evaluation. Owning BFS traversal lets us measure exactly which depth was used, cap node growth, compare depth 1 vs 2 vs 3, and teach the LLM to widen retrieval only when needed.

## V3 sequence

```text
POST /agent/run
   |
   +-- isolated_worktree? --yes--> detached Git worktree
   |
   +-- graph missing? --yes--> Graphify code-only extraction
   |
   v
Planner next action
   |
   +-- resolve_symbol
   +-- graph_query depth=1
   |       |
   |       +-- weak evidence --> model chooses depth=2 or better query
   |       +-- enough evidence -> read exact files
   |
   v
Coder patch
   |
   v
Reviewer targeted test/build
   |
   +-- inspect failure and iterate
   +-- git diff
   +-- finish with metrics
```

## Benchmark sequence

```text
POST /benchmarks/run
   |
   +-- graph_adaptive isolated worktree
   |       +-- graph tools enabled
   |       +-- optional validation command
   |
   +-- repo_scan isolated worktree
   |       +-- graph tools disabled
   |       +-- optional validation command
   |
   v
status + diff + correctness signals + token/cost deltas
```

## Scaling direction

For very large monorepos, the current in-memory graph loader can be replaced behind the same tool contract with SQLite, NetworkX, Neo4j, Memgraph, or a custom adjacency store. The agent protocol does not need to change as long as `graph_query` preserves bounded depth and diagnostics.
